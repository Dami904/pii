### 3.2 Poseidon2 — Critical Invariant (all three implementations must agree byte-for-byte)

**Parameters:** BN254 scalar field, **state width t=4, RATE=3, Hades MDS, S-box x^5, variable-length sponge, IV = (message_size) << 64, output = state[0].**

This is the Noir poseidon library v0.2.0 sponge as used by Wraith. The `Poseidon2::hash(arr, n)` call from that library is the reference. Every other implementation must produce identical output.

**Noir (circuits):** Use `dep::poseidon::poseidon2::Poseidon2` from the noir `poseidon` library v0.2.0. Call as `Poseidon2::hash([a, b], 2)`, `Poseidon2::hash([a,b,c,d], 4)`, etc. The second argument is the number of inputs (message size absorbed), NOT a capacity. **Do not switch to the Noir stdlib `poseidon2` unless you verify it uses the identical t=4 sponge with the same IV.** The Wraith codebase is the reference; match it exactly.

**Solidity (on-chain Merkle inserts):** The probe's 69,697 gas figure for Poseidon2 is **meaningless** (it was a skeleton without round constants). The real gas must be measured in Stage 0 with the ACTUAL library before any gas budget is committed. Target library: `zemse/poseidon2-evm` (Yul, BN254 t=4). Before using it, the golden-vector forge test (see Stage 0) MUST pass for `hash2(1,2)`, `hash2(0,0)`, `hash4(1,2,3,4)`, `hash7(1..7)`, AND the empty-tree root. If it does not match, the fallback is calling `nargo execute` from a precompile or replacing with an alternative library — both paths must still pass golden vectors.

**TypeScript SDK:** Use `@zkpassport/poseidon2` as the candidate. Before any note is committed, the SDK golden-vector test MUST pass for the same five vectors above (including empty-tree root). If `@zkpassport/poseidon2` fails any arity, switch to the Poseidon2 implementation inside `@aztec/bb.js`.

**Golden vectors (to be generated in Stage 0 from Noir):**
```
hash2(1, 2)             → <to be recorded>
hash2(0, 0)             → <to be recorded>
hash4(1, 2, 3, 4)       → <to be recorded>
hash7(1, 2, 3, 4, 5, 6, 7) → <to be recorded>
empty_tree_root_depth20 → zeros[20] = hash2(zeros[19], zeros[19]) → <to be recorded>
```
Record actual hex values after Stage 0 into `sdk/test/poseidon.golden.json`.

### 3.3 Key Derivation

```
spending_key              : random Fr (secret; lives only in browser wallet / local store)
owner_key   = hash2(spending_key, 0)   // public identity inside notes
viewing_key = hash2(spending_key, 1)   // for optional personal audit export

// Encryption keypair (for memo encryption — fixes Wraith's hash-only viewing key):
enc_secret  = hash2(spending_key, 2)   // deterministic 32-byte seed
enc_privkey = clamp(enc_secret)        // X25519 scalar (clamp per RFC 7748)
enc_pubkey  = X25519_basepoint(enc_privkey)  // 32-byte Curve25519 point
```

The enc_pubkey is shared publicly when the user wants to receive encrypted memos. It is also registered by issuers as an auditor pubkey so that share-note memos are encrypted to it.

### 3.4 Note Format (FINAL — after deposit-binding fix)

```
Note {
    asset_id  : Fr   // hash2(uint160(token_address), 0)
                     // USDC: hash2(uint160(0x3600...0000), 0)  [NOT 0; USDC is not native XLM]
    amount    : Fr   // < 2^64; USDC: 6-decimal atoms; shares: <= 6-decimal atoms (see §3.6)
    owner_key : Fr   // hash2(spending_key, 0)
    blinding  : Fr   // random Fr
}
commitment = hash4(asset_id, amount, owner_key, blinding)
nullifier  = hash2(commitment, spending_key)
```

**Deposit binding fix (CRITICAL — was broken in v1):** The original `deposit(token, amount, commitment)` accepted a caller-supplied commitment with no proof, creating a critical vulnerability: an attacker deposits 1 USDC with a crafted commitment that encodes 1,000,000 USDC and can later drain other users' funds. Fix: the contract computes the commitment itself. The depositor passes only a `secret = hash2(owner_key, blinding)` and the contract computes:

```
asset_id   = hash2(uint160(token), 0)           // on-chain
commitment = hash4(asset_id, amount, secret, 0) // note: slot 3 is 0 because secret already
                                                 //  absorbs blinding; OR keep full 4-field form
```

**Chosen approach (simpler, matches note format exactly):** User computes `commitment = hash4(asset_id, amount, owner_key, blinding)` off-chain AND also computes `secret_check = hash2(owner_key, blinding)`. Contract receives `(token, amount, commitment, owner_key_hash, blinding_hash)` — NO. This reveals `owner_key` on-chain.

**Final chosen approach:** deposit takes `(token, amount, commitment)` BUT the commitment is generated as:
```
commitment = hash3(asset_id, amount, hash2(owner_key, blinding))
```
where `hash3` means `Poseidon2::hash([asset_id, amount, hash2(owner_key, blinding)], 3)`. The contract recomputes the outer two fields (`asset_id` from the token address, `amount` from the calldata) and checks that `hash3(asset_id, amount, supplied_secret) == commitment`. The user supplies `secret = hash2(owner_key, blinding)`. This binds asset and amount without revealing owner_key or blinding, and the note format is consistent everywhere:

```solidity
// In deposit():
bytes32 asset_id = keccak256(abi.encode(token));  // NO — must use Poseidon2 for field consistency
bytes32 asset_id = poseidon2.hash2(uint160(token), 0);
require(poseidon2.hash3(asset_id, amount, secret) == commitment, "CommitmentMismatch");
```

And in circuits, the note preimage for a deposited note is `(asset_id, amount, owner_key, blinding)` but the leaf stored is `hash3(asset_id, amount, hash2(owner_key, blinding))`. All circuits must use this same 3-input commitment form for deposited notes.

**ALTERNATIVE (cleaner — recommended):** Keep the full 4-field `hash4` commitment everywhere and add a tiny `deposit` circuit that proves knowledge of the preimage:
```
// deposit circuit (public: commitment, asset_id, amount; private: owner_key, blinding)
assert(hash4(asset_id, amount, owner_key, blinding) == commitment)
```
This keeps one universal note format and costs one extra HonkVerifier deployment. The gas for deposit rises from ~450k to ~2.5M (estimate). This is the **recommended path** because it avoids the dual-format hazard. See §4.8 and Open Question A.

### 3.5 Order Format (FINAL — with expiry fix)

```
Order {
    side        : Fr   // 0 = buy, 1 = sell (base asset = share)
    price       : Fr   // limit price scaled by PRICE_SCALE = 10^7; < 2^64
    amount      : Fr   // base-asset quantity; < 2^64
    asset_base  : Fr   // share asset_id
    asset_quote : Fr   // USDC asset_id
    owner_key   : Fr   // trader's public identity
    nonce       : Fr   // random; prevents commitment collision
    expiry      : Fr   // Unix timestamp (seconds); < 2^64
}
order_commitment = hash8(side, price, amount, asset_base, asset_quote, owner_key, nonce, expiry)
```

`hash8` means `Poseidon2::hash([...8 inputs], 8)` (same sponge, 8-element message).

`PRICE_SCALE = 10_000_000` (10^7). All four arithmetic helpers (`geq64`, `min64`, `midpoint`, `mul_div_price`) operate on u64-range values after `assert_max_bit_size::<64>`.

### 3.6 Share Asset Decimals Constraint

Notes carry amounts < 2^64 ≈ 1.8 × 10^19. USDC (6 decimals, max note ≈ 18 trillion USDC) is fine. Share tokens MUST use **0–6 decimals on-chain**, NOT 18. Reasoning: with 18 decimals, 1 whole share = 10^18 atoms; a note could hold at most 18 whole shares before hitting 2^64. With 6 decimals, 1 whole share = 10^6 atoms; a note holds up to 18 trillion whole shares. Issued as a single genesis note, this is well within bounds. All share amounts in circuits, the SDK, and events use this low-decimal convention.

### 3.7 address_to_field (EVM — canonical)

```
address_to_field(addr) = uint160(addr)   // already < r; no mod needed in practice
asset_id(token)        = hash2(address_to_field(token), 0)
recipient_hash(addr)   = hash2(address_to_field(addr), 0)
```

`uint160(addr)` is at most 2^160, which is much less than r ≈ 2^254. The `mod r` is technically required for circuit soundness but is always a no-op for EVM addresses.

**USDC asset_id:** `hash2(uint160(0x3600000000000000000000000000000000000000), 0)` — the hashed form. USDC is NOT asset_id 0 (unlike Wraith's XLM special case). Reserve asset_id 0 as "unset/invalid" only.

**Share asset_id:** Each share asset is registered in `IssuerRegistry` at a sequential index `i`. `asset_id = hash2(i, 0)` where `i` is the registry index. This avoids needing an ERC-20 address (shares have no token contract) while keeping asset_ids unique and derivable from public data.

### 3.8 Merkle Tree

| Parameter | Value |
|---|---|
| Type | Incremental append-only binary |
| Depth | 20 |
| Capacity | 1,048,576 notes |
| Hash | `hash2` (Poseidon2 t=4 sponge, 2-input) |
| Empty leaf | `zeros[0] = 0`; `zeros[i+1] = hash2(zeros[i], zeros[i])` |
| Storage | Frontier: `uint256[20] filled_subtrees` (one hash per level) — precomputed zeros are constants, not recomputed on every insert |
| Root history | Ring buffer: `bytes32[100] roots` + `uint256 next_index`; ring slot = `next_index % 100` |

Path-bit convention: bit 0 = current node is LEFT child. Circuit enforces `bit * (1 - bit) == 0`.

### 3.9 Memo Encryption (fixes Wraith's missing real keypair)

Each non-zero output note gets an encrypted memo emitted in the event.

**Cipher:** X25519 ECDH + AES-256-GCM (both available in the browser via SubtleCrypto).

```
// For each output note going to recipient with enc_pubkey R:
ephemeral_priv = random_scalar()
ephemeral_pub  = X25519_basepoint(ephemeral_priv)
shared_secret  = X25519(ephemeral_priv, R)           // 32 bytes
enc_key        = HKDF-SHA256(shared_secret, "pii-note-memo-v1", salt=ephemeral_pub)
plaintext      = abi.encode(asset_id, amount, blinding, leaf_index, extra_data)
ciphertext     = AES-256-GCM(enc_key, nonce=random_12_bytes, plaintext)
memo           = ephemeral_pub ++ nonce ++ ciphertext   // 32 + 12 + len(pt) + 16 tag bytes
```

For share notes, an additional memo is encrypted to the issuer's auditor enc_pubkey (registered in IssuerRegistry). USDC-only notes are NOT encrypted to the issuer.

**ext_data_hash binding (fixes Wraith's non-enforcement):** For every proof-gated call (not deposit):

```
ext_data_hash = (keccak256(abi.encode(memos, relayer, fee, recipient_or_zero, block.chainid, pool_address))) mod r
```

The circuit receives `ext_data_hash` as a public input. The contract RECOMPUTES it from the calldata (memos array, relayer address, fee amount) and asserts the result equals the public input before calling the verifier. This prevents a front-runner from swapping memos or the relayer.

### 3.10 Relayer Pattern (fixes msg.sender identity leak)

Every proof-gated function is submitted by a relayer, not the user directly.

```
function submitProof(
    CircuitId circuit,
    bytes calldata proof,
    bytes32[] calldata publicInputs,
    bytes[] calldata memos,         // one per non-zero output note
    address relayer,
    uint256 relayerFee              // USDC atoms; must equal fee note amount in proof
) external
```

`msg.sender` is the relayer's hot wallet. The user's EVM address never appears on-chain for shielded operations. The relayer earns a fee note (shielded USDC) that is one of the outputs in the proof; it can later withdraw it normally. The relayer and fee are bound in `ext_data_hash`, so neither can be changed after proof generation.

**Deposit** is exempt (amounts are public by design; msg.sender identity leaks here, but this is unavoidable and documented in the threat model). Direct calls remain available as a fallback (user submits own tx, leaking identity).

## 4. Circuit Specifications

All circuits use Poseidon2 from `dep::poseidon::poseidon2::Poseidon2` (noir poseidon library v0.2.0).
All amounts and prices: `assert_max_bit_size::<64>()` before any arithmetic.
Integer arithmetic helpers (u64-safe after range check): `geq64`, `min64`, `midpoint` (floor), `mul_div_price` (floor, u128 intermediate).

**Public-input encoding (wire format):** each public input is one BN254 Fr element, encoded as 32 bytes big-endian, concatenated in declaration order. The contract parses `publicInputs` as `N × 32` bytes; any other length is rejected.

### 4.4 Circuit: `match_orders` (updated — full price-improvement refund, expiry check, matcher generates)

Proves two orders are compatible, computes fair midpoint execution, and correctly allocates all settlement notes including price-improvement refunds. Generated exclusively by the off-chain matcher.

**Public inputs (10):**
| # | Field | Description |
|---|---|---|
| 0 | `order_commitment_a` | Must be active on-chain |
| 1 | `order_commitment_b` | Must be active on-chain |
| 2 | `fill_note_buyer` | Buyer receives base-asset note |
| 3 | `fill_note_seller` | Seller receives quote-asset note |
| 4 | `residual_order_a` | Remaining order A (0 if fully filled) |
| 5 | `residual_order_b` | Remaining order B (0 if fully filled) |
| 6 | `refund_note_a` | Price-improvement refund for A (0 if none) |
| 7 | `refund_note_b` | Price-improvement refund for B (0 if none) |
| 8 | `now_bound` | `block.timestamp` upper bound; contract asserts `block.timestamp <= now_bound` and both order expiries > now_bound |
| 9 | `ext_data_hash` | Binds memos + relayer + fee |

**Private inputs:**
All fields of both orders (side, price, amount, asset_base, asset_quote, owner_key, nonce, expiry), plus output note blindings.

**Constraints (key):**
```noir
// 1. Recompute both order commitments (hash8 with expiry)
// 2. Opposite sides, same pair, buy_price >= sell_price
// 3. exec_price = midpoint(buy_price, sell_price) = floor((buy+sell)/2)
// 4. fill_amount = min64(buy_amount, sell_amount)
// 5. quote_filled = mul_div_price(fill_amount, exec_price, PRICE_SCALE)  [floor]
// 6. Settlement notes: buyer gets (asset_base, fill_amount), seller gets (asset_quote, quote_filled)
// 7. Price-improvement refund for buyer (fully filled):
//      buyer_locked = mul_div_price(buy_amount, buy_price, PRICE_SCALE)
//      refund_amount = buyer_locked - quote_filled
//      if refund_amount > 0: assert refund_note_a = hash4(asset_quote, refund_amount, buyer_key, r_blind)
// 8. Residual order (partial fill): re-commit with new nonce, same expiry
// 9. Expiry: assert both expiry_a > now_bound AND expiry_b > now_bound
// 10. All new note owner_keys proven in allowlist_root if share asset (matcher has this info)
```

**Estimated constraints:** ~12,000 gates → **~3.5M gas verify (estimate)**

### 4.6 Circuit: `buy_primary` (Pii-specific — replaces `issue_buy`)

Private primary purchase: investor spends shielded USDC, receives share note. Three outputs: share note (buyer), USDC change note (buyer), USDC fee note (platform). All amounts PRIVATE. The share qty is public at issuance only via the genesis event; individual trade sizes are hidden.

**Public inputs (9):**
| # | Field | Description |
|---|---|---|
| 0 | `merkle_root` | Commitment tree root |
| 1 | `usdc_nullifier` | Nullifier of consumed USDC input note |
| 2 | `share_out_commitment` | Share note for buyer |
| 3 | `usdc_change_commitment` | USDC change note for buyer |
| 4 | `usdc_fee_commitment` | USDC fee note for platform owner_key |
| 5 | `asset_id_usdc` | USDC asset_id (constant; bound to prevent asset substitution) |
| 6 | `asset_id_share` | Which share offering |
| 7 | `kyc_and_allowlist_root` | Hash of (kyc_root ++ allowlist_root); contract verifies each individually |
| 8 | `ext_data_hash` | Binds memos + relayer + fee |

> `kyc_and_allowlist_root` is split for the contract's live-root checks. In the circuit it is `hash2(kyc_root, allowlist_root)` — a single field that cryptographically binds both roots without exposing them individually. The contract provides its current roots, computes `hash2(current_kyc, current_allowlist)`, and checks equality against public input 7. This means both roots must be current (or within the allowed staleness window).

**Private inputs:**
```
usdc_note_amount, usdc_note_blinding, spending_key,
usdc_merkle_path[20], usdc_merkle_indices[20],
share_amount,
share_blinding,
usdc_change_amount, usdc_change_blinding,
platform_fee_amount, platform_fee_blinding,
price_usdc,            // offering price; must match issuer-registered value
fee_bps,               // must match registry value
platform_owner_key,    // platform's owner_key; must match registry value
kyc_path[20], kyc_indices[20],
allowlist_path[20], allowlist_indices[20]
```

**Constraints:**
```noir
let owner_key = Poseidon2::hash([spending_key, 0], 2);
// 1. USDC input note ownership + Merkle
let usdc_comm = Poseidon2::hash([asset_id_usdc, usdc_note_amount, owner_key, usdc_note_blinding], 4);
assert(Poseidon2::hash([usdc_comm, spending_key], 2) == usdc_nullifier);
assert(check_merkle(usdc_comm, ...) == merkle_root);
// 2. Price enforcement: usdc_paid = ceil(share_amount * price_usdc / SHARE_SCALE)
//    using u128 intermediate to avoid overflow
let usdc_paid = ceil_mul_div(share_amount, price_usdc, SHARE_SCALE);
// 3. Fee: platform_fee_amount = ceil(usdc_paid * fee_bps / 10000)
let fee = ceil_mul_div(usdc_paid, fee_bps, 10000);
// 4. Value conservation
assert(usdc_note_amount == usdc_paid + usdc_change_amount);
assert(platform_fee_amount == fee);
// 5. KYC + allowlist membership
let kr = check_merkle(owner_key, kyc_path, kyc_indices);
let ar = check_merkle(owner_key, allowlist_path, allowlist_indices);
let combined = Poseidon2::hash([kr, ar], 2);
assert(combined == kyc_and_allowlist_root);
// 6. Output notes
let sc  = Poseidon2::hash([asset_id_share, share_amount, owner_key, share_blinding], 4);
assert(sc == share_out_commitment);
let cc  = Poseidon2::hash([asset_id_usdc, usdc_change_amount, owner_key, usdc_change_blinding], 4);
assert(cc == usdc_change_commitment);
let fc  = Poseidon2::hash([asset_id_usdc, platform_fee_amount, platform_owner_key, platform_fee_blinding], 4);
assert(fc == usdc_fee_commitment);
// 7. Range checks
share_amount.assert_max_bit_size::<64>();
usdc_change_amount.assert_max_bit_size::<64>();
platform_fee_amount.assert_max_bit_size::<64>();
```

**Estimated constraints:** ~10,000 gates → **~3.5M gas verify (estimate)**

### 4.7 Circuit: `claim_dividend` (Pii-specific — private claim amount)

Proves a share note exists in the dividend snapshot root. Outputs a shielded USDC note whose amount equals `note_amount × rate` (both private). Does NOT consume the share note.

**Public inputs (5):**
| # | Field | Description |
|---|---|---|
| 0 | `snapshot_root` | Merkle root at dividend snapshot height (from DividendManager) |
| 1 | `claim_nullifier` | `hash2(hash2(share_commitment, spending_key), dividend_id)` — prevents double-claim without spending share note |
| 2 | `asset_id_share` | Binds claim to a specific offering |
| 3 | `dividend_id` | Distribution identifier (epoch); from DividendManager |
| 4 | `usdc_out_commitment` | Shielded USDC note for claimant (amount hidden) |

> `recipient_hash` and `claim_amount` are NOT public. The recipient is implicit (the claimant proves their own spending key). The USDC amount is hidden, solving the privacy leak from v1. The contract does not need the amount — it tracks `claimed_total` via a different mechanism (see §8.5).

**Private inputs:**
```
share_note_amount, share_note_blinding, spending_key,
snapshot_merkle_path[20], snapshot_merkle_indices[20],
usdc_rate,             // public param from DividendManager: total_usdc / total_shares
usdc_out_amount,       // = floor(share_note_amount * usdc_rate / RATE_SCALE)
usdc_out_blinding
```

**Constraints:**
```noir
let owner_key      = Poseidon2::hash([spending_key, 0], 2);
let share_comm     = Poseidon2::hash([asset_id_share, share_note_amount, owner_key, share_note_blinding], 4);
let root           = check_merkle(share_comm, snapshot_merkle_path, snapshot_merkle_indices);
assert(root == snapshot_root);
// Claim nullifier: unique per (note, dividend_id); does not consume the share note
let inner_null     = Poseidon2::hash([share_comm, spending_key], 2);
let claim_null     = Poseidon2::hash([inner_null, dividend_id], 2);
assert(claim_null == claim_nullifier);
// Amount: usdc_out = floor(share_note_amount * usdc_rate / RATE_SCALE)
// usdc_rate = total_usdc_distributed / total_shares_at_snapshot, stored as a scaled integer
// Soundness: claim_amount <= share_note_amount * usdc_rate / RATE_SCALE
//            therefore sum of all claims <= total_shares * usdc_rate / RATE_SCALE = total_usdc
let computed_out = mul_div_rate(share_note_amount, usdc_rate, RATE_SCALE);
assert(usdc_out_amount == computed_out);
usdc_out_amount.assert_max_bit_size::<64>();
// USDC output note (recipient is the prover's owner_key — no separate recipient_hash needed)
let uc = Poseidon2::hash([USDC_ASSET_ID, usdc_out_amount, owner_key, usdc_out_blinding], 4);
assert(uc == usdc_out_commitment);
```

**Soundness argument:** `usdc_rate = floor(total_usdc × RATE_SCALE / total_shares)`. Each claim is `floor(note_amount × usdc_rate / RATE_SCALE) ≤ note_amount × total_usdc / total_shares`. Sum over all notes ≤ total_shares × (total_usdc / total_shares) = total_usdc. The treasury's unsold shares (still owned by issuer's owner_key as part of the genesis note or later split notes) are included in total_shares at snapshot; the issuer must claim dividends on those shares itself (or accept the funds remain in the pool). Notes split or merged AFTER the snapshot: only notes IN the snapshot root can claim; a note created after the snapshot is not a leaf in snapshot_root and cannot produce a valid Merkle proof.

**claimed_total tracking:** the contract tracks `claimed_total` per dividend_id as a running USDC sum. This sum is updated by each `claimDividend` call... but the amount is private. **Resolution:** the USDC output commitment is inserted into the main Merkle tree (the claimant can spend it later). The contract does NOT track claimed_total in USDC; instead, it tracks the count of valid claim nullifiers. The issuer can reclaim `funded_usdc - total_remaining` after expiry by observing the total of all withdrawn USDC amounts from dividend-related notes. This is a **privacy trade-off** accepted per OQ4 decision (a): unclaimed USDC stays in the pool permanently (no expiry-based reclaim). This avoids any claimed_total accounting. The issuer pre-funds generously and accepts that dust may remain. See Open Question C for the expiry-with-tracked-total alternative.

**Estimated constraints:** ~5,500 gates → **~2.5M gas verify (estimate)**

### 4.8 Circuit: `deposit` (optional — fixes commitment binding)

A tiny circuit that ZK-proves the depositor knows a valid note preimage for the commitment they are depositing. This is the **recommended** path over the `hash3` contract-recomputation approach (see §3.4), because it preserves one universal note format.

**Public inputs (3):**
| # | Field | Description |
|---|---|---|
| 0 | `commitment` | The note commitment being inserted |
| 1 | `asset_id` | Must match `hash2(uint160(token), 0)` for the deposited token |
| 2 | `amount` | Must match the ERC-20 transferFrom amount |

**Private inputs:** `owner_key, blinding`

**Constraints:**
```noir
assert(commitment == Poseidon2::hash([asset_id, amount, owner_key, blinding], 4));
```

**Estimated constraints:** ~500 gates → **~2.0M gas verify (estimate)**

The contract verifies the ZK proof, then calls `safeTransferFrom` for the exact `amount` of `token`, computes `asset_id = hash2(uint160(token), 0)` on-chain, and asserts it matches public input 1. An attacker cannot deposit 1 USDC with a commitment encoding 1,000,000 USDC because the circuit constrains `amount == public amount == actual transferred amount`.

**KYC root staleness window:** 50 recent roots stored. A proof generated against root[i-3] is still valid if root[i] is current. This gives investors a grace period when the platform updates the KYC list. Revocation of a specific investor: the platform rotates the KYC root excluding that key. Old proofs referencing old roots remain valid for 50 root-rotations (~hours to days depending on update frequency). A revoked investor can always exit (withdraw, cancel orders) using proofs against a root where they were still listed. This is the standard Zcash-style "recent root" window; the revocation latency is the window size times the root update cadence.

## 8. Threat Model and Privacy Analysis

### 8.1 What Remains Public (on-chain)

| Data | Public? | Notes |
|---|---|---|
| Deposit token + amount | **YES** | Unavoidable; ERC-20 safeTransferFrom is public |
| Deposit timing + depositor address | **YES** | msg.sender on deposit; by design |
| Withdrawal token + amount | **YES** | Required for ERC-20 safeTransfer |
| Withdrawal recipient | **YES** | Required for transfer |
| Genesis supply (per share asset) | **YES** | GenesisIssuance event; total supply always public |
| Issuer identity + asset metadata | **YES** | AssetRegistered event |
| Dividend funding total + rate | **YES** | DividendProposed event; `total_usdc` and `usdc_rate` are public |
| Order expiry | **YES** | Public input in place_order (OQ5 decision) |
| Existence of any shielded operation | **YES** | Tx on-chain; timing visible |
| Shielded balances | No | Only opaque commitments |
| Transfer amounts + parties | No | ZK only |
| Share ownership (individual) | No | No public ERC-20; only opaque commitments |
| Primary buy qty + USDC paid | No | Both private in buy_primary circuit |
| Order price / amount / side | No | Only commitment hash |
| Trader identity | No | owner_key ≠ EVM address; relayer submits |
| Dividend claim amount | No | Hidden in claim_dividend circuit (v3 fix) |
| Whether two deposits are same investor | **Possibly** | Timing/amount correlation |
| Allowlist membership of any investor | No | ZK membership proof; owner_key private |
| KYC status of any investor | No | Same |
| Cap table | No | Rebuilds only for auditor with enc_privkey |

### 8.2 Privacy Leaks (documented, accepted or mitigated)

**L1 — Deposit/withdraw correlation:** same amount in then out is strong correlation. Mitigation (v2): fixed-denomination deposits.

**L2 — Genesis supply is public:** total share supply is visible. This is accepted (securities regulation typically requires public disclosure of total authorized shares).

**L3 — Dividend rate reveals total payout:** `rate × total_supply = funded_usdc` is computable from public data. Individual holders' shares are still hidden.

**L4 — Order expiry reveals order TTL:** order lifetime is public (OQ5 decision accepted).

**L5 — Timing correlation:** placing an order shortly after a deposit, or claiming a dividend shortly after a deposit, may correlate with the depositor.

**L6 — Relayer metadata:** the relayer sees the pre-image data (note content, tx timing). Use of a trusted relayer (e.g. the matcher server) is a documented trust assumption. Anyone can run a relayer; users should run their own if maximum privacy is required.

**L7 — Matcher trust model** (same as Wraith §11):

| Matcher can do | Matcher cannot do |
|---|---|
| See order price, amount, pair, owner_key | Steal funds (ZK-enforced settlement) |
| Choose match priority, censor orders | Modify execution price (proven in circuit) |
| See which orders are pending | Know the EVM address behind owner_key |

**L8 — KYC/allowlist correlation:** an investor joining the allowlist followed by a shielded op correlates timing. Mitigation: batch allowlist updates, random delays.

### 8.3 Security Properties

| Attack | Prevention |
|---|---|
| Deposit over-commitment (CRITICAL) | deposit circuit proves preimage; asset + amount bound on-chain |
| Double-spend | Nullifier mapping; ZK-enforced |
| ext_data_hash griefing / memo swap | Contract recomputes ext_data_hash from calldata; asserts match |
| Price manipulation (dark pool) | Midpoint execution proven in circuit; cannot deviate |
| Fake order in match | Order preimage committed and verified in match circuit |
| Front-running orders | Orders opaque (commitment only visible pre-match) |
| Replay attack | ext_data_hash binds chainid + pool address + memos |
| Dividend double-claim | Per-dividend claim nullifier, not the share note nullifier |
| Over-issuance | Genesis note fixes max supply; no additional mint function |
| Unauthorized primary buy | KYC + allowlist Merkle proofs in circuit |
| Unauthorized issuer | IssuerRegistry.approveIssuer gated by platform admin |
| Expired order execution | match_orders checks expiry against block.timestamp |
| Revoked investor exit | Old allowlist/KYC roots stay valid for 50 rotations → investor can still cancel orders and withdraw during grace period |
| Overflow / underflow | 64-bit range checks on all amounts and prices |
| Identity from msg.sender | Relayer pattern; depositor address leaks only on deposit |
| PiiPool upgrade risk | Immutable on testnet; no proxy |

### 8.4 Trusted Parties

| Party | Can do | Cannot do |
|---|---|---|
| Platform admin | Approve/revoke issuers, update KYC root, set fee bps (≤10%), pause new deposits | Steal funds, break ZK proofs, block withdrawals |
| Issuer | Register assets, update allowlist, propose dividends, set auditor pubkey | See individual holdings without auditor key, steal USDC |
| Matcher | See order details (price, amount, pair, owner_key), choose match priority | Steal funds, change execution price, know EVM address |
| Relayer | See proof + plaintext note content before submission | Steal funds (proof is already signed); can front-run timing (but not swap memos — ext_data_hash bound) |
| Auditor (issuer's enc_privkey) | Decrypt share-note memos, rebuild cap table | Anything on-chain without spending key |

## 10. Open Questions

**OQ-A — RESOLVED: Universal note format, hash3 deposit.**
Use ONE note format everywhere: `commitment = hash3(asset_id, amount, secret)` where `secret = hash2(owner_key, blinding)`. Deposit: user passes `(token, amount, commitment, secret)` and the contract computes `asset_id = hash2(uint160(token), 0)`, then asserts `hash3(asset_id, amount, secret) == commitment`. No deposit circuit needed; deposited and transacted notes are identical. The nullifier remains `hash2(commitment, spending_key)`. **All circuit specs and §3.4 are updated below in §14 (Changes from v3-draft).** The deposit circuit (§4.8) is eliminated; circuit count drops from 8 to 7. Gas for deposit drops to ~450k (no ZK verify).

*Note format (FINAL, supersedes §3.4):*
```
secret     = hash2(owner_key, blinding)          // user computes off-chain; never revealed
commitment = hash3(asset_id, amount, secret)      // hash3 = Poseidon2::hash([a,b,c], 3)
nullifier  = hash2(commitment, spending_key)      // unchanged
```
All 7 remaining circuits replace every `hash4(asset_id, amount, owner_key, blinding)` with `hash3(asset_id, amount, hash2(owner_key, blinding))` — equivalently, circuits receive `secret` as a private input computed from `(owner_key, blinding)` and use `hash3(asset_id, amount, secret)`. The note preimage tuple is `(asset_id, amount, secret)` on the wire; `(asset_id, amount, owner_key, blinding)` in the wallet.

**OQ-B — RESOLVED: 50 KYC/allowlist roots, 7-day time bound.**
Store 50 recent roots in the ring buffer AND enforce a 7-day wall-clock bound: a root is only accepted by the contract if `block.timestamp <= root_timestamp + 7 days`. The contract stores `(root_value, inserted_at)` pairs. This prevents an old root from being valid indefinitely even if the ring buffer has not rotated past it. With at most daily updates, 50 roots = 50 days of history, far exceeding the 7-day validity window — so the time bound is the binding constraint, not the ring size. Revoked investors have at most 7 days to exit (cancel orders, withdraw) using proofs against a root that still includes them.

**OQ-C — RESOLVED: (a) unclaimed USDC stays locked permanently.**
No expiry, no claimed_total tracking, no recovery. This fully preserves privacy (no per-claim amount leaks). The issuer pre-funds `rate × total_supply` USDC. Treasury shares (unsold genesis note held by issuer's own owner_key) are included in total_supply; the issuer must claim dividends on those itself, receiving its own shielded USDC note. Only floor-division dust (at most 1 atom per note) remains permanently locked. Issuers must be informed of this before funding in the UI.

**OQ-D — RESOLVED: v1 client-side JSON viewing bundle, user-chosen recipient.**
`wallet.exportViewingBundle(assetIds[])` produces a signed JSON file containing: decrypted note data for the chosen assets, the user's enc_pubkey, a timestamp, and the user's wallet address (optional). The recipient is whoever the user chooses (auditor, regulator, personal record). No on-chain action required. Schema is simple and open — no per-jurisdiction format imposed in v1. Not blocking.

**OQ-E — RESOLVED: single matcher in v1, permissionless matching.**
MVP uses one matcher service, but `matchOrders` is callable by ANYONE who knows both order preimages (no access control on the contract function). Cancel is always available. A second matcher can be added in v2 without any contract change. Not blocking.

## 11. Changes from v1 (original plan)

| Change | Reason |
|---|---|
| **Deposit binding redesigned (CRITICAL)** | v1 accepted caller-supplied commitments with no proof — allows inflation attack. v3 requires a ZK deposit circuit (or hash3 recomputation) that binds asset and amount on-chain. |
| **ext_data_hash now enforced on-chain** | v1 never recomputed it; a front-runner could swap memos or relayer. v3 contract recomputes from calldata for every proof-gated call. |
| **Withdraw now supports change output** | v1 was whole-note only. v3 adds `change_commitment` public input and constraints. |
| **Order format now includes expiry** | v1 had no expiry (known limitation). v3 adds `expiry` to the order preimage as `hash8`; it is a public input so the contract can reject expired orders. |
| **match_orders now pays full price-improvement refund** | v1 kept buyer's price improvement locked in residual. v3 refund circuit correctly computed. |
| **Viewing key replaced by real ECDH keypair** | v1 used a hash-only viewing_key with no encryption scheme. v3 derives an X25519 enc_keypair from spending_key; memos use ECDH + AES-256-GCM. |
| **Zeros precomputed as constants** | v1 noted this as a Soroban-vs-EVM concern. v3 stores `ZEROS[20]` as immutable constants in PiiPool constructor. Ring buffer replaces Vec.remove(0). |
| **Relayer pattern added** | v1 had direct user tx submission (msg.sender leaks identity). v3 all shielded ops go through a relayer whose address appears on-chain instead. |
| **Poseidon2 golden-vector gate moved to Stage 0** | v1 had it in Stage 1. v3 makes it the first gate because every subsequent component depends on it being byte-identical. |
| **Share decimals constraint formalized** | v1 used 18-decimal shares without noting the 2^64 note limit would cap at 18 shares. v3 mandates 0–6 decimals for share assets. |
| **EVM asset_id uses hashed form for USDC** | v1 was ambiguous (asset_id 0 reserved for USDC vs. hashed). v3 uses `hash2(uint160(0x3600...0000), 0)` for USDC; asset_id 0 = unset/invalid. |
| **Share asset_id from registry index** | v1 used `hash2(address_to_field(shareToken), 0)` — requires an ERC-20 address. v3 uses `hash2(registryIndex, 0)` since there is no token contract. |
